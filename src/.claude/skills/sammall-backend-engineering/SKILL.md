# SamMall 后端工程化工作流

## 概述
当你在 **SamMall 仓库内部** 处理后端任务时，使用这个 skill。

目标不是单纯把代码写出来，而是让改动**贴合当前项目的技术栈、目录结构、代码分层和已有实现习惯**。优先做小而准的修改，避免脱离仓库现实去重新设计一套架构。

## 项目基础认知
在真正改代码前，先结合当前仓库重新确认现状；但默认从下面这些认知出发：

- 这是一个基于 Go 的后端项目。
- Web 框架使用 Gin。
- 应用启动与依赖装配集中在 `src/main.go` 与 `src/router`。
- 配置由本地 yaml 或远程 etcd + Viper 加载。
- `src/adaptor` 负责数据库、Redis、外部依赖适配。
- `src/service` 负责核心业务逻辑。
- `src/api` 负责 HTTP 请求处理与响应输出。
- `src/adaptor/repo/model` 与 `src/adaptor/repo/query` 下存在生成代码，应优先复用。
- Redis 已用于验证码、ticket、频控、token、临时状态等场景。
- 当前项目近期重点在后台登录、滑块校验、验证码、鉴权链路。

## 适用场景
遇到以下任务时优先使用本 skill：

- 新增或修改后端接口
- 修复请求链路、鉴权、验证码、后台用户管理相关 bug
- 判断新逻辑应该放在哪一层
- 审查某次改动是否破坏当前分层
- 分析一个需求会影响 `router/api/service/adaptor/repo/config/utils` 中哪些模块
- 从性能、稳定性、安全性、测试完整性角度审视后端改动
- 在编码前给出工程化改动方案
- 在编码后做工程化自检

以下情况不适用：

- 纯前端或 UI 工作
- 与本仓库无关的泛 Go 问题
- 纯产品脑暴但不落到当前代码仓库的实现讨论

## 核心工作原则

### 1. 先尊重仓库现状，再提出方案
在给出改动方案前，先阅读实际代码路径，确认当前实现方式。

至少要先搞清楚：
- 当前功能由哪个路由或入口接入
- 当前请求会经过哪个 controller / service / adaptor 链路
- 现有 repo/query 生成代码是否已经覆盖所需表访问
- Redis / config / common / utils 里是否已经有可复用模式

如果仓库里已经有现成模式，不要凭空再造一套本地架构。

### 2. 严格遵守分层边界
除非你读到的代码明确说明不是这样，否则默认遵守以下边界：

- `src/router`
  - 注册路由
  - 组织路由分组
  - 挂载中间件
  - 处理鉴权白名单与整体接入关系
- `src/api`
  - 绑定 HTTP 参数
  - 参数转换
  - 调用 service
  - 输出统一响应
- `src/service`
  - 承载核心业务逻辑
  - 组织业务规则
  - 协调多个 adaptor
  - 处理领域层面的校验
- `src/adaptor`
  - 访问 DB / Redis / 外部依赖
  - 管理基础设施相关实现
- `src/config` / `src/common` / `src/utils` / `src/consts`
  - 提供共享配置、错误码、常量、工具能力

同时遵守这些反规则：
- 不要把核心业务逻辑塞进 handler。
- 不要把明显的 HTTP 细节带进 service，除非仓库现有代码已这样设计且你只是做局部修复。
- 如果现有生成 query/repo 模式可满足需求，不要绕开它写临时 SQL。
- 不要直接手改 `.gen.go`，除非用户明确要求且你确认了生成策略。

## 任务分类方法
在动手前，先判断任务类型：

| 任务类型 | 首先要识别什么 |
|---|---|
| 新功能 / 新接口 | 路由入口、请求 DTO、service 入口、持久化影响 |
| Bug 修复 | 失败路径、当前行为、最小责任层 |
| 重构 | 真实边界问题、重复逻辑、回归风险 |
| 鉴权 / 登录 / 验证码 | 白名单、中间件、Redis 状态、token 生命周期、失败分支 |
| 性能优化 | 重复查库、重复 Redis 访问、无效序列化、热路径 |
| 测试 / 验证 | 编译路径、关键分支、手工验证方案 |

如果你在做分析、设计或代码审查，应该先明确写出任务类型。

## 标准分析顺序
针对 SamMall 后端任务，优先按以下顺序思考并输出：

1. **任务类型**
   - 这是新功能、bug 修复、重构、性能任务还是验证任务。
2. **涉及分层**
   - 哪些层会受影响：`router/api/service/adaptor/config/utils`。
3. **改动放置位置**
   - 每一段新增逻辑应该放在哪里，为什么。
4. **现有模式复用点**
   - 当前仓库有哪些文件、流程、写法可以照着延续。
5. **风险点**
   - 是否涉及鉴权、Redis 状态、DB 一致性、生成代码等风险。
6. **验证方案**
   - 在宣布完成之前，应如何验证改动。

## 推荐输出格式
当用户让你分析需求、给出改动方案、或者审查代码时，尽量按下面结构输出：

```markdown
## 任务类型
- 新功能 / Bug 修复 / 重构 / 性能优化 / 测试补充

## 涉及模块
- router:
- api:
- service:
- adaptor/repo:
- config/common/utils:

## 建议改动点
1. ...
2. ...

## 分层放置理由
- ...

## 风险点
- ...

## 验证清单
- ...
```

如果任务很小，可以简写；但只要涉及多层改动，就不要省略“分层放置理由”。

## 仓库特定指导

### 路由与控制器链路
当你要新增或修改一个接口时，通常按下面顺序检查：

1. `src/router/router.go`
2. 对应的 `src/api/admin` 或 `src/api/customer`
3. 对应的 `src/service`
4. 对应的 `src/adaptor`
5. DTO / common / consts 定义

如果是后台接口，优先确认：
- 它是否应放在现有 admin 鉴权中间件下
- 是否需要加入白名单
- 是否会影响当前 token 获取逻辑

### 登录 / 鉴权 / 验证码相关任务
这类任务属于高敏感链路。

至少检查：
- 白名单是否正确
- 中间件 token 解析和用户查询链路
- Redis 中 captcha / ticket / token / 密码错误次数 等状态键的生命周期
- 用户状态是否正确校验（启用 / 禁用）
- 失败路径是否有过期、重放、脏状态残留问题

当任务和登录有关时，额外关注：
- 密码校验路径
- 密码错误次数限制
- 滑块或验证码 ticket 校验
- token 生成、落 Redis、过期时间
- Redis 中间状态失效后的行为是否合理

### 数据访问
优先复用现有生成代码。

在新增 repo 逻辑前，先检查：
- `query` 下是否已存在可用表访问入口
- 数据访问逻辑是否应继续放在 adaptor/repo 体系中
- 是否有必要新增查询封装，而不是把 GORM 逻辑散落到 service 里

### 配置与可观测性
如果任务影响启动、配置、运行时行为，要优先检查：
- `src/config/config.go`
- `src/main.go`
- 当前 logger 的使用方式
- health check / pprof 是否受影响

除非任务明确要求扩大范围，否则保持与现有 logger、common error 风格一致。

## 代码风格要求
优先遵守仓库现有风格，而不是把外部最佳实践硬套进来。

推荐：
- 做小步、局部、可验证的改动
- 沿用现有命名和目录组织
- 延续 admin/customer 的领域划分
- 复用当前 DTO、errno、const 定义方式
- 优先直接清晰的控制流，而不是过度抽象

避免：
- 为一次性逻辑新建泛化 helper 层
- 在修一个小 bug 时顺手重构大面积无关代码
- 重排大量无关格式
- 给显而易见的逻辑加注释
- 轻易新建目录，除非现有结构明显放不下

## 性能审查清单
如果任务和性能有关，或者该链路本身属于热路径，重点检查：

- 单次请求内是否重复查库
- 是否有不必要的 Redis 往返
- 是否存在重复序列化 / 反序列化
- 热路径里是否打印了过重日志
- 鉴权、验证码链路中是否有可避免的同步耗时步骤
- 启动阶段连接检查或配置加载是否引入额外阻塞

不要做脱离现状的“想象式优化”；每一个性能建议都要绑定到你已经读过的实际路径。

## 安全与正确性检查清单
后端改动，尤其是鉴权相关改动，需要至少检查：

- HTTP 边界的参数绑定与校验是否合理
- 禁用用户、未授权用户的行为是否正确
- captcha / ticket / token 是否存在重放、过期、脏状态问题
- 白名单是否放大了暴露面
- 是否把内部错误细节直接暴露给前端
- Redis / DB 状态更新是否存在部分成功、部分失败的问题

## 测试与验证要求
这个仓库当前可能没有很完整的自动化测试，因此验证不能省略，只能更明确。

对于非平凡的后端改动，至少验证：
- 能编译通过
- 受影响接口能跑通
- 成功路径正常
- 代表性的失败路径正常
- 如果改了鉴权，未登录 / 无权限路径正确
- 如果改了 Redis 临时状态，过期 / 删除 / 重试行为合理

如果改动涉及登录 / 鉴权 / 验证码，请明确验证：
- 正常请求成功
- 错误密码失败
- 错误或过期验证码 / ticket 失败
- 禁用用户不能通过
- 无 token 或非法 token 被拒绝
- Redis 中计数器、ticket、token 的过期和清理符合预期

如果仓库缺少自动化测试，请给出简短但明确的手工验证清单，不要假装“已经充分覆盖”。

## 常见错误

| 常见错误 | 更好的做法 |
|---|---|
| 把业务规则直接写进 handler | handler 保持薄，业务逻辑进入 service |
| 在 service 中临时直写 DB 逻辑 | 复用 adaptor/repo/query 模式 |
| 新增后台接口时忽略白名单和中间件影响 | 先检查 router 和鉴权挂载方式 |
| 直接修改 `.gen.go` | 修改生成来源或在非生成文件外包一层 |
| 未验证就宣称完成 | 先运行检查或给出明确验证步骤 |
| 借修 bug 顺手大面积改造无关代码 | 保持范围与任务一致 |

## 示例

**用户请求：**
“给后台新增一个修改管理员密码的接口，并保证走现有登录鉴权体系。”

合格的响应应该体现：
- 先判断这是一个后端新功能任务
- 先检查 `router/api/service/adaptor` 中 admin 用户链路
- 明确请求绑定放在 `src/api/admin`
- 明确密码更新规则应放在 `src/service/admin`
- 复用现有 admin user 数据访问模式
- 检查该接口是否仍应挂在现有 admin 鉴权中间件之下，而不是加入白名单
- 提醒关注密码存储一致性、登录兼容性、验证步骤

## 最终原则
在 SamMall 仓库里，优先追求**贴合当前项目**，而不是追求“看起来更高级”。

先读代码，再设计改动；把逻辑放到正确层次；尽量复用现有模式；编码前说清风险；完成前给出验证证据。
